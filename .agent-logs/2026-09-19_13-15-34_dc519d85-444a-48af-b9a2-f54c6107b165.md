## Summary — what was wrong and what I fixed

**The functionality:** Meeting Intelligence is the Groq-generated **summary, key points, decisions, action items, and important moments**, built from the real transcript and stored in the `MeetingIntelligence` table. `GET /meetings/{id}/intelligence` returns `ready` (row exists), `generating` (transcript exists, no row), or `unavailable` (no transcript).

**Why it was stuck on "Generating…":** Generation ran **exactly once**, best-effort, inside `run_process_transcript` (right after the transcript is saved). There was **no retry and no on-demand path**. So any meeting whose single attempt didn't persist a row stayed on "Generating…" forever — which happens when the meeting was transcribed **before** that generation code existed, or the one Groq call had a transient failure/race (it's swallowed and never retried). `GROQ_API_KEY`/`GROQ_MODEL` *are* configured, so it wasn't a global config problem — it was the missing retry/backfill.

**The fix (additive, no existing contracts changed):**
- **Backend** — new `POST /meetings/{id}/intelligence` (`backend/app/api.py`) that schedules the existing **idempotent** `generate_intelligence(meeting_id)` in a background task (owner-scoped; no-op if a row already exists or there's no transcript). This backfills old meetings and retries transient failures.
- **Frontend** (`MeetingInsights.tsx`) — when it sees `generating`, it now **auto-kicks that endpoint once**, keeps polling, and shows a **"Try again"** button so the state is recoverable instead of a dead spinner.

So: open a stuck meeting → the workspace triggers (re)generation → polling picks up the `ready` content within a few seconds (assuming Groq responds). If Groq errors, "Try again" retries.
